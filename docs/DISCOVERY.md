# DriveSweep — Drive Discovery

Measured on this machine (`Darwin 25.6.0`, Apple Silicon) on **2026-09-07**.
Every number below came from `du -x -s -m` on the real path, not an estimate.

> **Units.** All sizes are **GiB** (base-1024, what `du` reports). macOS's Storage pane
> uses **GB** (base-1000). `410.69 GiB` == `~441 GB`. This 7.4% gap is the single most
> common reason a disk tool looks "wrong" next to Finder. See [Gotcha 1](#1-gib-vs-gb).

### Your "Documents: 177.21 GB" is not a folder

`~/Documents` is 0.76 GiB. The Storage pane's "Documents" is a **file-type
classification applied across the whole disk** — every file that isn't an app, a photo,
or a known system type. Your `~/code` tree, your caches, your archives all land in it.
Same for "Developer" (51.88 GB) which does not map to any single directory.

**Design consequence:** DriveSweep must never try to reproduce Apple's categories. They
are not directories and cannot be reconciled path-by-path. Report real paths and real
`du`-equivalent sizes, and say so explicitly in the UI.

## 2. Safety classification

Four tiers. The distinction that matters to a developer is not "is this a cache" but
**what does it cost me to get it back.**

### Tier S — Safe: regenerates automatically, costs seconds

| Path | Size | Regenerated by |
|---|---|---|
| `/Library/Developer/CoreSimulator/Caches/dyld/*` | **23.87** | First launch of each simulator runtime |
| `~/Library/Developer/Xcode/DerivedData` | **29.13** | Next Xcode/`xcodebuild` build |
| `~/Library/Caches/typescript` | 2.83 | Next `tsc` / editor session |
| `~/Library/Caches/ccache` | 5.00 | Next native build (slower until warm) |
| `~/Library/Logs` | 3.94 | Continuously; nothing reads old ones |
| `~/Library/Caches/com.apple.dt.Xcode` | 0.01 | Xcode |
| project `android/**/build`, `ios/build` | 7.04 | Next build |

**Subtotal ≈ 72 GiB.**

The dyld cache is the best find on the machine: 23.87 GiB, invisible in every
GUI disk tool because it sits under `/Library` (not `~/Library`), and it is pure
derived data — deleting it costs one slow simulator boot.

### Tier R — Safe but re-download: regenerates over the network

Deleting these is safe; the cost is bandwidth and time, and **it breaks offline work.**

| Path | Size | Cost to restore |
|---|---|---|
| `~/Library/Caches/CocoaPods/Pods/External/React-Core-prebuilt` | **44.84** | Re-download per RN version on next `pod install` |
| `~/Library/Caches/CocoaPods` (rest) | 18.50 | `pod install` |
| `~/.npm/_cacache` | 33.39 | `npm install` |
| `~/.bun/install/cache` | 16.64 | `bun install` |
| `~/Library/pnpm` + `~/Library/Caches/pnpm` | 19.17 | `pnpm install` |
| `~/.yarn` | 5.05 | `yarn install` |
| `~/.gradle` | 8.14 | Next Gradle build |
| `~/.expo/ios-simulator-app-cache` | 6.78 | Re-download Expo Go / dev client |
| `~/.expo/expo-go` | 4.34 | Re-download Expo Go |
| `~/.expo/android-apk-cache` | 2.38 | Re-download |
| `~/Library/Caches/ms-playwright` | 0.77 | `playwright install` |
| `~/Library/Caches/Cypress` | 0.52 | Cypress postinstall |
| `~/Library/Caches/Homebrew` | 0.11 | `brew` re-download |
| `~/.npm/_npx` | 4.13 | Re-fetched on demand |

**Subtotal ≈ 165 GiB.** This is the largest reclaimable bucket by far.

`React-Core-prebuilt` at 44.84 GiB deserves its own callout: React Native 0.81+
caches prebuilt React Core artifacts per version *and* per build configuration. A
developer who has touched several RN versions accumulates tens of GiB here silently.
No RN tool prunes it.

### Tier C — Caution: regenerates, but you lose state

| Path | Size | What you lose |
|---|---|---|
| `~/Library/Developer/CoreSimulator/Devices` | **98.36** | Installed apps, app data, logins, granted permissions, keychains |
| `~/.android/avd` | 17.19 | Same, per AVD; AVD definitions too |
| `~/Library/Caches/com.swmansion.radon-ide/Devices` | 13.14 | Radon IDE device state |
| `~/Library/Developer/Xcode/iOS DeviceSupport` | 11.07 | Symbols per iOS build; re-fetched only by re-pairing that physical device |
| `~/Library/Android/sdk/system-images` | 26.29 | AVDs referencing a deleted image stop booting |
| `~/Library/Android/sdk/ndk` | 21.24 | Builds pinned to a removed NDK version fail |
| Simulator runtimes (see §3) | 32.53 mounted / 56.1 reported | Devices on that runtime become unavailable |

**Subtotal ≈ 220 GiB.** Real money, but every deletion here has a consequence a
developer will notice, sometimes days later. This tier is why DriveSweep needs
per-item explanations, not a single "Clean" button.

Concrete example from this machine: one booted simulator
(`24F387D5…`, iPhone 17 / iOS 26.5) holds **39.72 GiB**, of which **34.19 GiB** is
`data/Containers/Data` — accumulated app data, not the OS image. `simctl erase` on that
one device reclaims ~34 GiB and costs only re-installing dev builds. That is a far
better trade than deleting a runtime, and no GUI tool surfaces it.

Also worth noting: 8 Android NDK versions coexist (21.4 → 27.1) totalling 21.24 GiB.
Most projects pin one. But the pin lives in `build.gradle`/`gradle.properties`, so
DriveSweep can *read* which versions are actually referenced before recommending.

### Tier D — Do not touch automatically

| Path | Size | Why |
|---|---|---|
| `~/code` source (non-derived) | ~25 | Your work. Uncommitted changes are unrecoverable. |
| `~/code/**/.git` | 8.90 | History; may hold unpushed commits |
| `~/Library/Application Support/*` | 57.61 | App state, tokens, licences, unsynced notes |
| `~/Library/Group Containers` | 3.00 | Same |
| `/Applications` | 34.53 | Reinstall required; some are paid/licensed |
| `~/Documents`, `~/Downloads`, `~/Desktop` | 1.73 | User data |
| `/opt/homebrew` | 9.31 | Managed by `brew`, not by file deletion |
| `~/.asdf` | 3.79 | Active toolchain; deleting breaks every shim |

`node_modules` sits at the boundary: **257 directories, 32.03 GiB** across `~/code`
(56% of that tree). Mechanically regenerable — but only if the lockfile resolves, the
registry is reachable, and the project isn't pinned to something yanked. Treat as
Tier R for projects with a lockfile and Tier D without one.

## 3. What developers actually run into

### 1. GiB vs GB
`du` is base-1024, Finder and the Storage pane are base-1000. A tool reporting
`410.69` next to Finder's `441` looks broken. **Label the unit in the UI and offer a
toggle.**

### 2. Sparse files: `st_size` is a lie
```
Docker.raw   apparent (ls -l / st_size):  60 GB
             actual   (du / st_blocks):    8.1 GB
```
A 7.4x error on a single file. Disk images (`.raw`, `.qcow2`, `.dmg`, `.sparsebundle`),
Core Data stores, and some SQLite files are all sparse.
**Always size from `st_blocks`, never `st_size`.** `expo-file-system`'s `File.size`
returns `st_size` — see [PLATFORM.md](./PLATFORM.md).

### 3. Cryptex: 56 GB that filesystem walking cannot see
Simulator runtimes are no longer plain directories. They are read-only APFS volumes
mounted `nobrowse` under:
```
/Library/Developer/CoreSimulator/Cryptex/Images/bundle/SimRuntimeBundle-<UUID>
```
`du -x` (single-filesystem, which you need to avoid double-counting) **skips them
entirely**. `du` without `-x` reports 32.53 GiB for the mounted subset, while
`xcrun simctl runtime list` reports **7 images totalling 56.1 GB**.

There is no correct filesystem-only answer here.
**Runtimes must be enumerated and deleted via `simctl runtime list` /
`simctl runtime delete`, not by path.** Same class of problem for
`simctl delete unavailable`.

### 4. Hardlinks and clones cause double-counting
`pnpm` stores one copy in `~/Library/pnpm` and hardlinks into every `node_modules`.
APFS `cp -c` clones behave the same way. Summing per-directory sizes therefore
**over-reports**, and "freeing" a linked copy frees nothing until the last link dies.
**Track `(st_dev, st_ino)` and count each inode once per scan.**

### 5. Overlapping categories double-count too
Measured live: android `build` dirs under `~/code` total 12.54 GiB when counted
naively, but only a fraction lies outside `node_modules`. The rest was counted twice.
**Rules must be evaluated against a tree with explicit precedence and pruning, not as
independent globs.**

Re-measured with the native scanner, which matches the basename exactly and prunes
`node_modules`: **31 dirs, 6.34 GiB**. The earlier 7.04 GiB figure here came from
`find -path "*/android/*build"`, which also matches names merely *ending* in
"build" — it was picking up `*_autolinked_build` CMake artifact directories under
`android/app/.cxx/`. Those are genuine build output (~0.65 GiB) but are not named
`build`, so a rule keyed on that name does not and should not claim them. The
lesson generalises: **a glob that looks precise can quietly widen a category**, so
the number and the rule that produced it have to be reported together.

### 6. A full walk is genuinely slow
The data volume holds **9.8M inodes**. Measured wall-clock for a single `du`:

| Path | Size | Time |
|---|---|---|
| `~/.bun` | 16.98 | 76 s |
| `~/Library/pnpm` | 14.68 | 66 s |
| `~/Library/Developer/CoreSimulator/Devices` | 98.36 | 65 s |
| `~/Library/Application Support` | 57.61 | 116 s |
| `~/.npm` | 37.67 | 39 s |
| `~/Library/Android` | 51.86 | **7 s** |

Time tracks **file count**, not bytes: `~/Library/Android` is 3x bigger than `~/.npm`
and 5x faster. A naive full-home scan exceeded **10 minutes** in testing.

**Design consequence:** scan the known-hotspot catalog first (results in seconds),
stream results as they arrive, cache with mtime invalidation, and treat a full
exhaustive walk as an explicit opt-in.

### 7. TCC / permissions
Reading `~/Library` requires **Full Disk Access**, granted by the user in System
Settings and not requestable programmatically. Without it, directories return empty
rather than erroring — so a scan silently reports 0 GiB instead of failing.
**Detect the denial explicitly** (probe a known-nonempty path) and tell the user, or
every number in the UI is quietly wrong. See [PLATFORM.md](./PLATFORM.md).

### 8. Deleting a booted simulator's files corrupts it
`24F387D5…` is `Booted` right now. Removing files under a running device's `data/`
leaves CoreSimulator inconsistent. **Check `simctl list devices` state and refuse, or
shut down first** — never delete under a live device.

### 9. Trash is not free space
Moving 100 GiB to `~/.Trash` reclaims nothing. Either delete outright (with consent)
or report "pending in Trash" honestly.

### 10. Things that only their owning tool can safely remove
- `/opt/homebrew` → `brew cleanup`
- `~/.asdf` → `asdf uninstall`
- Docker images/volumes → `docker system prune` (deleting `Docker.raw` destroys all volumes)
- Simulator runtimes → `simctl runtime delete`
- Android SDK components → `sdkmanager --uninstall`

For these, DriveSweep should **surface the size and recommend the command**, not
unlink files.

## 4. Reclaim summary for this machine

| Tier | Size | Character |
|---|---|---|
| S — safe, auto-regenerates | ~72 GiB | Effectively free |
| R — safe, re-download | ~165 GiB | Costs bandwidth; breaks offline |
| C — caution, loses state | ~220 GiB | Needs per-item consent |
| **Plausible total** | **~240–290 GiB** | Tier S + R + selective C |

The single best-value actions, in order:

1. `simctl erase` the 39.72 GiB booted device → **~34 GiB**, near-zero cost
2. Delete `React-Core-prebuilt` → **44.84 GiB**, re-downloads per RN version
3. Delete simulator dyld caches → **23.87 GiB**, costs one slow boot
4. Clear `DerivedData` → **29.13 GiB**, costs one rebuild
5. Prune `~/.npm/_cacache` + `~/.bun` + pnpm store → **~69 GiB**, re-downloads
6. Drop 7 unused Android NDKs → **~18 GiB**, after checking Gradle pins

## 5. Reproducing this

`scripts/scan.sh` runs the catalog in `src/catalog.ts` with 8-way parallelism and
emits TSV. It is the same code path the app will call natively.

```sh
./scripts/scan.sh                       # catalog scan, ~2 min
./scripts/scan.sh --json                # machine-readable
```
